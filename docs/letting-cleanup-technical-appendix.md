## Target model

## The minimum model (three tables own facts; everything else reads through)

**1. property_units — the physical master.** One row per physical space; owns name, address/UPRN, floor, nia/gia/itza sqft, use class, condition, EPC. The tracker GET already COALESCEs it over the cache (`routes.ts:4859-4870`); the public feed does NOT (`publicListingColumns` `routes.ts:4221-4245` reads available_units raw) — both flip to master-only in the same deploy, then the cache columns go.

**2. tenancy_schedule_units — the lease spine.** One row per occupancy; owns tenant, lease dates, passing rent, ERV, quoting rent, rates/SC, and OCCUPANCY ONLY via the 0032 `occupancy_status` column, finally written (Vacant / Trading / Holding Over / Lease Event / Archived). No pipeline status. Link: property_unit_id → property_units. No deal_id, no letting_tracker_unit_id. Its link columns are never severed wholesale: the tenancy import re-links children by identity after a replace, and a row DELETE with a live deal attached re-points or refuses.

**3. crm_deals — the one record of a letting, from birth** (Woody 2026-10-26). Owns deal_ref (#), deal_type, bgp_acting_for, status (the ONLY pipeline status; 'ARCH' declared as a closed code or mapped to WIT — and included in every closed-status list, including the one-live-deal index predicate and the floor-plan 'active deal' test), fee + fee_percentage + deal_fee_allocations, agreed rent, agents (internal_agent_ids), parties, dates, and **Heads of Terms via deal_hots** (the per-unit `available_units.hots_content` document migrates into a deal_hots draft version so a fresh cycle starts with clean HOTs). Links: unit_id → property_units (the physical unit, kept — it is what the deal page's Unit box edits and what 20+ joins use, and it is NOT letting-specific: advisory deals carry it too) and tenancy_unit_id → spine (the current occupancy; derivable from unit_id once tenancy.property_unit_id is complete). `stage` stays as a derived/read column until its eight readers switch.

**4. available_units, shrunk to marketing-only data, keyed by deal_id, KEEPING ITS id.** show_on_website, rent_poa, lease_terms, available_date, marketing_start_date, restrictions, location, notes, scheme; photos/brochures, viewings, offers, interest, briefs hang off it. It carries NO status, fee, rent, sqft, floor, use class, EPC, unit_name, agents or HOTs — all read through deal → unit/spine. Its id survives because it IS the public URL (`/leasing/<id>`) and the key of every viewings consumer; one row per live letting deal; "delete a unit from the tracker" becomes "withdraw the deal".

**5. leasing_schedule_units — client strategy layer, read-through.** Keeps zone/positioning/priority/targets/updates/status_band; status DERIVED from the live deal (CODE_TO_LEASING) plus occupancy; linked by tenancy_unit_id only. Own phase (1101 rows, 82% unlinked).

**6. evidence_plan_units and 7. property_plan_units — per-plan layers, same treatment.** Both keep their geometry/label and link to the physical unit (property_plan_units.unit_id → property_units is canonical; tenancy_unit_id is the derived occupancy pointer for both; evidence_plan_units gains unit_id in its own phase); both derive status from the shared `effectiveStatus(deal) + occupancy_status` rather than a private vocabulary (`property-plan-links.ts:148-160` goes); property_plan_units.status_override stays only as an explicit manual override shown as such; their editors write occupancy or override, never pipeline status.

## The Letting Tracker becomes a VIEW of letting deals; the Deals board already shows them

`GET /api/available-units` ≈ `SELECT … FROM crm_deals d LEFT JOIN property_units pu ON pu.id = d.unit_id LEFT JOIN tenancy_schedule_units t ON t.id = d.tenancy_unit_id LEFT JOIN available_units m ON m.deal_id = d.id WHERE isLettingDeal(d) AND legacyToCode(d.status) IN (tracker statuses)`. ## Woody's rule, stated precisely against stored values

- **Letting deal types (LETTING_DEAL_TYPES):** deal_type IN ('New Letting', 'Lease Disposal') as Woody named them, plus 'Temp Lease' and 'Licence' (the code already treats them as lettings at `unit-mirror.ts:373` and `available-units.tsx:3191`), plus legacy 'Letting'/'Leasing' until `normaliseDealType` rewrites them. NOT Lease Acquisition / Sub-Letting / Tenant Acquisition (tenant-rep on someone else's unit), NOT Lease Renewal / Rent Review / Regear / Dilapidations / Service Charge (advisory on an occupied unit — these share crm_deals.unit_id with lettings and must never be refused by a letting rule), NOT Sale / Purchase / Consultancy. Import-anything's private types ('Tenant Rep', 'Assignment', 'Investment Sale/Acquisition') are mapped onto the dropdown set at ingest.
- **Marketing = AVA, Negotiation = NEG** (`shared/deal-status.ts:9-10`; legacy labels fold via legacyToCode). Recommended to include HOT and OPP in the tracker's live set. SOL stays a live pill; EXC/COM/WIT/INV (+ARCH) fold under Historic.
- **Forward rule (deal ⇒ tracker):** every crm_deals row with deal_type ∈ LETTING_DEAL_TYPES AND legacyToCode(status) ∈ {OPP, AVA, NEG, HOT, SOL} [Woody's minimum {AVA, NEG}] has exactly one tracker row, and that row IS the deal — whichever door created the deal (deal form, WIP cell, ChatBGP, WIP import, import-anything, generic route, Add Unit).
- **Reverse rule (tracker ⇒ deal):** every tracker row has deal_id NOT NULL pointing at a letting-type deal; its Ref # is crm_deals.deal_ref. Re-marketing a let/withdrawn unit starts a NEW deal (fresh cycle, already built) with fresh HOTs.
- **Side:** `bgp_acting_for` is derived from deal_type on CREATE (New Letting / Temp Lease / Licence → 'landlord'; Lease Acquisition / Sub-Letting / Tenant Acquisition → 'tenant'; Lease Disposal → whichever Woody decides); the deal-page pill stays as the override; the column becomes NOT NULL. Because the derivation changes the Landsec classification (`account-resolver.ts:362-371`), the PO party (`deal-po.ts:19`) and the WIP client column for every NEW tenant-side deal, it ships only after Woody has seen the Phase 0 impact list — it is not a silent refactor. ## Points raised by the final critique (addressed in this revision where possible)

- **major** — A seventh unit table is missing from the map: property_plan_units (floor-plan outlines). It has its own unit_id -> property_units link, a tenancy_unit_id link and a status_override column, and property-plan-links.ts derives a unit status from it with yet another private vocabulary that reads available_units.marketing_status, tenancy.status, leasing.status and an active_deals filter excluding only WIT/COM/INV (not EXC, not ARCH). The proposal cites property-plan-links.ts:102/130/146 as a marketing_status reader but never names the table, its two link columns or status_override; Phase 4's property_units DELETE-guard extension names evidence_plan_units but not property_plan_units.unit_id; Phase 1's vocabulary consolidation and Phase 6's 'evidence-plan layer' both miss its twin.
- **major** — Two live write paths into crm_deals and leasing_schedule_units that bypass every mirror, gate and normalisation are absent from the current model, the 'status writers that bypass every mirror' list, the 'deal-creation code for a unit' list, rule 5 ('crm_deals.status is written only through setDealStatus'), rule 17 ('deals created by any door go through POST /api/crm/deals normalisation') and the retire list: (a) the generic CRM routes — PATCH /api/generic/:table/:id and POST /api/generic/:table/bulk-update (up to 500 rows) accept crm_deals and leasing_schedule_units, run no mirror/legacyToCode/client-scope, and have no client callers, so they are an unused but reachable way for any logged-in user to rewrite deal status; (b) universal-ingest ('import anything' from WhatsApp captions, email, SharePoint, the global drop zone and the leasing page) raw-INSERTs/UPDATEs crm_deals and leasing_schedule_units with its own deal_type vocabulary ('Tenant Rep', 'Assignment', 'Investment Sale', 'Investment Acquisition' — none in the dropdown), no status normalisation, no acting-for, no tracker row — exactly the AVA/NEG deals Woody's ask #2 would surface.
- **major** — Rule 4 and Phase 2 step 5 contradict each other and, as written in Phase 2, would break ordinary advisory work. Rule 4 says 'one live landlord-side LETTING deal per physical unit (0034 re-keyed on crm_deals.unit_id)'; Phase 2 step 5 says the re-keyed index is 'deal-type-agnostic as today'.
